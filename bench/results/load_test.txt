Load generated by k6 in Docker against the gateway on this machine, with the
mock upstream holding every request for 100 ms. Total latency below is
what the client saw and is therefore mostly the mock; overhead is the gateway's
own histogram (total minus upstream, per request), scraped either side of each
run and diffed. Overhead percentiles are interpolated within histogram buckets,
so they are estimates whose error is the width of the bucket they landed in.

Overhead bucket bounds (ms): 1, 2, 3, 5, 7.5, 10, 15, 20, 30, 50, 100, 250

'offered' is the arrival rate k6 was told to hold; 'achieved' is what it
managed. Load is offered at a rate rather than by a fixed pool of workers,
because a pool that waits for each reply slows down when the service does and
reports its own patience as the service's capacity.

'client p50' is what k6 saw from inside its container, and is mostly the mock.
'upstream mean' is what the gateway waited on, and is the column that says
whose fault a bad row is. The mock is a single Python process on the same
laptop as the gateway, the database and the load generator, so it saturates
too: a row where both columns climb together is the machine running out, not
the gateway. Only a row where overhead climbs and the upstream does not is a
statement about this code.

The overhead percentiles are read off a bucketed histogram, so they are printed
as the bucket they landed in wherever the bucket is wide relative to the value.
The mean beside them is not an estimate: it is the histogram's own sum over its
own count, and it is the number to compare between rows.


BURST, 40/s for 20s, 160/s for 10s, then quiet again

   phase  requests       p50       p95       p99
  before       801   120.3ms   122.3ms   127.1ms
   spike      1515   739.9ms  1491.6ms  1890.9ms
   after       798   120.1ms   127.4ms   470.6ms

The row that matters is 'after' against 'before'. A gateway that queued the
spike rather than shedding it is still working through the queue long after the
spike ended, and the caller sees a service that never came back.


DEGRADED UPSTREAM, 20% of upstream calls failing, 10% of requests asking for 3000 ms

                        requests   failed  unexpected  overhead p99
      healthy upstream      1801     0.0%           0       15-20ms
     degraded upstream      1800    11.1%           0       15-20ms

What the caller got back, by status:

     200      1601    88.9%   served
     429       198    11.0%   rate limited, the provider's or the gateway's
     503         1     0.1%   upstream overloaded, or the gateway out of pool

'failed' is what the caller saw, after the gateway's retries had already
absorbed what they could. 'unexpected' counts statuses outside the set a
degraded upstream is allowed to produce, and is the number that should be zero:
the upstream failing is not the gateway failing. Status 0 is k6's code for a
request that got no status at all - a timeout or a reset - which is the one
outcome a gateway is supposed to prevent, because it is the one the caller
cannot tell apart from the gateway being down.

Identical prompts in an identical order, the same number of workers both
times, with the tenant's entries deleted before the cold run. This is the one
scenario driven by a fixed amount of work rather than an arrival rate, because
the comparison is how long the same work took.
