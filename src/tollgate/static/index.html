tollgate.danmccabe.dev

A gateway for model API traffic.

It sits between an application and a model provider. It authenticates tenants, enforces rate limits and spend budgets, caches what it can, inspects traffic in both directions, and records every token.

You have reached the gateway itself, not a product. There is nothing to sign up for: every request needs a tenant key, and keys are issued from a CLI. This page explains what is behind the hostname — the code, the reasoning and the measurements are all in the repository.

Adoption

One line changes.

Request and response bodies stay byte-compatible with the provider's API, so an application adopts the gateway by pointing the official SDK at it. Streaming, error shapes and the SDK's own retries keep working. 

from google import genai

client = genai.Client(
    api_key="tg_...",  # a tenant key, not the provider's
    http_options={"base_url": "https://tollgate.danmccabe.dev"},
)
print(client.models.generate_content(
    model="gemini-3.7-flash", contents="Hello").text)

The provider credential lives in the gateway's environment and is never visible to a tenant. The same code runs locally against a mock provider, so the repository can be cloned and used without a provider key and without spending anything.

Why

Why a gateway exists.

An application that calls a model API directly has no good answer to a handful of questions:

  • Which customer spent what, this month, on which model?
  • What happens when one of them gets stuck in a retry loop?
  • Did a user smuggle instructions into a prompt?
  • Did a response leak a credential or personal data?

Once more than one team, customer or feature calls the API, each call site reimplements the same rules, and spread across services those rules drift apart. A gateway puts them in one place on the request path, and it is the only component that sees every token in both directions.

Request path

How a request flows.

Six stages between the client and the provider. Every one of them can end the request, and the chip on the right says how.

1

Authenticate the tenant

The key is hashed and looked up. The tenant it resolves to is the only one this request can ever read or spend against.

401
2

Rate limit and budget

A per-tenant token bucket in Redis, and month-to-date spend against a budget reserved before the call, then reconciled after it. Rate limits fail open; budgets do not.

429 · 402
3

Inspect the input

A regex baseline, then a pinned ONNX classifier looking for prompt injection. Off, monitor or block, per tenant; monitor by default.

403
4

Look in the cache

A versioned hash over the normalised request, scoped per tenant, with an optional pgvector similarity tier. A hit is replayed as a real event stream.

200, no spend
5

Call the provider

The tenant's key is removed and the provider's attached. Responses are relayed event by event and never buffered.

upstream error
6

Scan the output, record the usage

Credential and PII scanning with a hold-back window, then an append-only ledger row priced in integer micro-cents.

403

The return path is the hard part: output scanning wants a complete response, and streaming never provides one. A hold-back window contains a leak on a stream rather than noticing one after it has gone out.

Capabilities

What it does.

Each of these works the way it does for a reason, and the reasons are written up in the design notes.

Passthrough, streamed and not

Server-sent events are relayed event by event, with usage parsed out of the stream, so accounting survives a client hanging up mid-response or an upstream failing after a 200 has already gone out.

Tenant auth

Keys stored only as SHA-256 hashes, revocable, several live per tenant. The provider credential stays in the gateway and never reaches a caller.

Rate limits and spend budgets

Token buckets in Redis, a versioned price table, money in integer micro-cents, and a budget reserved before the upstream call then reconciled when the stream ends.

Two-tier cache

An exact hash over the normalised request, scoped per tenant, plus an optional pgvector similarity tier. Cached responses are replayed as real event streams.

Detection both ways

Injection detection on the way in; credential and PII scanning on the way back, with a hold-back window on streams. Off, monitor or block, per tenant.

Observability

One OpenTelemetry trace per request, with the upstream call as its own span, so the gateway's own overhead separates from the provider's latency. No prompt or response text reaches a span, a metric label or a log line, and a test enforces it.

Deployment

What this hostname is.

An ECS Fargate task behind an application load balancer, deployed from main by GitHub Actions, on infrastructure declared in Terraform.

On the request path
Python 3.13, FastAPI and uvicorn, httpx to the provider. 0.25 vCPU and 512 MB, running non-root on a read-only filesystem.
State
Postgres 17 with pgvector for tenants, keys, prices, the ledger and cache entries. Redis for buckets, spend counters and reservations, all with a TTL.
Secrets
The database URL and the provider key come from Secrets Manager. The pipeline authenticates with OIDC and stores no keys.
Build and ship
Lint, types and tests, then an image built and deployed by digest, migrations run with the exact code being deployed, a smoke test, and a rollback if it fails.
Observe
OTLP traces and Prometheus metrics to Grafana Cloud, one trace per request, with the dashboard and its alert declared in Terraform.
Trust boundaries
Who trusts what, and what happens when each piece is compromised, is written up in the threat model.
